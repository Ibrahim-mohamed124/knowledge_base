Kubernetes does not automatically send a signal (like SIGHUP) to your application process when a ConfigMap or Secret is modified. Instead, dynamic zero-downtime configuration updates rely on two mechanisms working in sync: Atomic Volume Mounts at the Kubernetes infrastructure level, and Dynamic File Reading at the application level.

Part 1: How Kubernetes Updates Files (Atomic Volume Mounts)

When you mount a ConfigMap or Secret as a volume into a Pod, Kubernetes creates a specific directory structure on the pod's filesystem using symlinks:

Plaintext

 

/etc/config/ (Mounted Volume Path)
├── app.json -> ..data/app.json (Symlink to current dataset)
├── ..data -> ..2026_09_22_09_17_59.123456789 (Symlink to active timestamped directory)
└── ..2026_09_22_09_17_59.123456789/ (Real directory containing files)
    └── app.json

The Atomic Update Process

When you update the ConfigMap via kubectl apply:

The kubelet detects the change (typically within its sync period, ~60 seconds).

It creates a new hidden directory containing the updated files (e.g., ..2026_09_22_09_25_00.987654321/).

It creates a temporary symlink pointing to this new directory.

It performs an atomic swap on the ..data symlink using the rename() system call.

It cleans up the old timestamped directory.

Why "Atomic"? The rename() operation is atomic at the OS kernel level. Your application will never read an incomplete, partially written, or corrupted file during an update. At any fraction of a millisecond, reading app.json will resolve to either 100% of the old config or 100% of the new config.

Part 2: How Applications Pick Up Changes (Dynamic File Reading)

Because Kubernetes only updates the filesystem contents, your application must be designed to react to those updates without restarting the container.

1. Inotify / File Watchers (Event-Driven)

Languages provide filesystem monitoring libraries (e.g., Node.js fs.watch, Go fsnotify, Java WatchService) that listen for OS kernel notifications.

Crucial Caveat: Do not watch the individual file directly (e.g., /etc/config/app.json). Because Kubernetes updates configs via symlink swaps, a watcher pinned to the specific file's inode will stop receiving events after the symlink is swapped.

The Fix: Watch the parent directory (/etc/config) or watch for changes to the ..data symlink itself.

2. Read-on-Demand (Polling / Request Lifetime)

Instead of keeping configuration in static memory at startup, load config values per request or poll the file at set intervals:

Python

 

# Example: Reading configuration per incoming request or on-demand
import json

def get_config():
    with open('/etc/config/app.json', 'r') as f:
        return json.load(f)

def handle_request():
    config = get_config()  # Always fetches the latest atomic state from disk
    # ... process request using dynamic config ...

Important Exceptions & Caveats

subPath Mounts break atomic updates: If you mount a ConfigMap using subPath (e.g., mounting a single file directly into an existing directory), Kubernetes loses the symlink structure. Files mounted via subPath will not update dynamically.

Propagation Delay: ConfigMap updates are not instant. Kubelet sync period + local cache TTL means changes usually take between 10 to 90 seconds to reflect on disk inside the container.

Environment Variables do not update: If you inject ConfigMap keys into env or envFrom variables inside your Pod spec, they are set once at container creation time. Changes to the ConfigMap require a full Pod restart/rollout to update environment variables.
